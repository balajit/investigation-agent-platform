## 8. §4 Java parsing (`application/analysis/java/`), Spring config, range banking

Note on location: `_is_range_read` lives in `application/investigation/verification.py:3127-3148`, not in `execution.py`; `boundary_facts.py` is about declared Spring DI/config bindings and runtime-mechanism markers, not module boundaries — the module/service boundary logic is in `context_compiler.py`.

### 8.1 Direct answers

| Question | Answer |
|---|---|
| Newer Java constructs: silent gap or loud failure? | **Mostly silent gap.** Records, compact constructors, sealed/permits, `instanceof` patterns, switch expressions with `yield`, text blocks, `var`, and `_` all parse with `has_error=False`, but the fact layer simply does not enumerate switch expressions/arrow cases, enum constants, interface constants, or nested-type methods, and emits **no limitation code** for what it skipped. The result ("field_not_found" / no record) is indistinguishable from "absent" (J5). Syntax errors, in contrast, are handled partially: `window_facts` checks a declaration subtree (J4). |
| Can a definition window split a signature from its body, or attribute a nested/lambda block to the wrong method? | **Yes, the second.** Lambda and anonymous-class bodies are credited to the enclosing method (J1) and anonymous-class fields to the outer class (J2). Signature/body splitting is bounded by the window reader (annotations above the method and multi-line signatures are the risk; the file-stem fallback also misattributes windows that start inside a secondary class, J8). |
| Are boundaries detected or assumed? | **Assumed from path prefix.** A file is "external" when it is outside every `source_roots`/`paths` entry (`context_compiler.py:910-935`); an empty root list classifies everything as external, the opposite of what the comment in `reasoning.py:965-980` promises (J9). |
| Where does dataflow stop; is it documented? | Intra-procedural, text-ordered, no CFG (J3). Stopping points are typed only for passed-as-argument, concurrent visibility, stream laziness, and out-of-window reference (`dataflow.py:196-262`); receiver mutation, lambda capture, and field stores are not flagged. The frontier cannot tell "found nothing" from "gave up" (J10). |
| Spring precedence? | **No.** Not modeled anywhere; emitted values carry no precedence or uncertainty qualifier (J11, J12). It can cite a value runtime would override. |

## 9. §5 Retrieval, authorization, tenant isolation

### 9.1 Direct answers

| Question | Answer |
|---|---|
| Fail-closed + degrade-to-empty, or fail the run loudly? | **Fail-closed per action is right; failing the run is not.** The deny is a typed BLOCKED result with a `miss_reason` (not an empty list), returned before `record_retrieval_attempt` (`execution.py:1205` vs `~4446`), so it costs a turn but spends no retrieval budget and leaves no stamp (R8). The loop "survives" a permanently denied SEARCH_LOGS only because one rule remembers it (`forcing.py:1259-1280`). What is missing is the *class-level* outcome: when the only capability a claim needs is denied, the run should abstain immediately with an explicit `CAPABILITY_DENIED` handoff rather than burn turns and surface as generic `INSUFFICIENT` (R9). Add a profile lint at onboarding: enabled claim kinds whose required capability is denied. |
| Is the second deny reason real? | **Dead.** `ProfileBasedCapabilityRegistry.is_capability_enabled` ignores tenant/profile (`profile_authorizer.py:137-142`), so "Capability … is disabled" fires only for unknown names (R6). |
| Next double/under-count edge? | Several, below (R10). The most severe: a scope-less stored query makes the requery loop unbounded. |
| Cross-tenant read path? | **Yes** — R1 (SHARED knowledge) and R2 (log index prefix). Core repositories (evidence, hypothesis, investigation, timeline, findings, jobs, profile) all carry `tenant_id` predicates; workflow IDs and signals are gated by a tenant-scoped repo lookup first (404, not 403); pagination cursors are HMAC-bound to tenant and investigation; MCP derives scope from transport authentication; `rls_session` uses transaction-local `SET LOCAL`, so no pool leak (all **R**). |
