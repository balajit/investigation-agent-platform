# Comparative Review Methodology — Docs vs Code (COMP_REVIEW)

**Status:** Methodology v1.0 — must be approved before verification starts. **Ground rule (code wins):** code is ground truth for behavior; documentation bends to code. If code implements a decision better than the docs describe, update the docs to reflect code. If docs promise functionality the code does not implement, file it as a tracked gap item for a coding agent. Never edit code to match stale docs during this review.

**Scope:** all `docs/IAP-implementation*` (Parts 1–11 plus addenda, operations, plan-todo, openapi-spec, appl-profile, dynamic-mapping design), `docs/IAP-functional-view-v0.2.md` (baseline for v0.3), and extension docs (`ADD_SCHEMATHESIS*`, `ui-backend-openapi-typed-models-design.md`, `SYSTEM_API_Live_Findings_TODO.md` where they touch behavior). Code surface is `src/investigation_agent_platform/` (`domain/`, `application/`, `ports/`, `infrastructure/`, `api/`, `bootstrap/`, `mcp/`, `integrations/`), plus `config/`, `migrations/`, `tests/`, `main.py`, and worker entrypoints.

**Coding-standards authority:** `~/bin/AGENTS.md` (project-agnostic base) applies to every unit in this review, as adapted to IAP in `C13` below. Documented IAP deviation: the base `Settings` example uses `env_file=".env"`; IAP forbids secrets in any `.env` or committed file per user direction — secrets come only from runtime-injected env vars or a secret manager (AWS Secrets Manager, OpenBao, or equivalent), `.env` files stay git-ignored and secret-free, and any committed secrets file is a gap. Reason: a secrets file in the repository defeats rotation, audit, and least-privilege handling that a manager plus runtime injection provides.

## 1. Review categories (what gets reviewed and what good looks like)

### C1 — Configuration (maintainability, standard form, secrets, env variance)

Good means one typed source of truth (`src/investigation_agent_platform/infrastructure/configuration/config.py` with frozen Pydantic models and `extra="forbid"`), env-first overrides under a single `IAP_*` namespace, and secrets that never live in the repository in any form — no `.env` files with secrets, no YAML secrets, no committed secrets files. Secrets arrive only via runtime-injected environment variables or a secret manager (AWS Secrets Manager, OpenBao, or equivalent) resolved at process start; `.env.<env>` files may document only non-secret keys and defaults, and any `.env` used locally must be git-ignored and secret-free, with `SecretStr` types plus redacted logs throughout.

Checks: list every `IAP_*` var read in `config.py` and confirm each has a documented owner, default, and required/optional flag per env (`development`, `test`, `staging`, `production`); classify each var as secret or non-secret and confirm every secret resolves only from runtime env injection or secret-manager lookup (AWS Secrets Manager, OpenBao, or equivalent) with no secrets file committed to the repository and no secret values in `config/application.yaml`, `config/logging.yaml`, or any `.env.<env>`; confirm `config/application.yaml` and `config/logging.yaml` contain only non-secret defaults and match `PlatformSettings` schema; confirm fail-closed production guards (`IAP_DATABASE_URI`, per-provider `IAP_<PROVIDER>_API_KEY`, `IAP_ELASTIC_CURSOR_SIGNING_KEY`, Azure/Muse required fields) actually halt boot with a named error; confirm no `SecretStr.get_secret_value()` output reaches logs; confirm unknown-field rejection is fail-closed. Cadence for env variance: maintain a single `config/env-matrix.md` (or appendix table in the architecture doc) with columns `variable`, `development`, `test`, `staging`, `production`, `secret?`, `secret source (runtime env vs manager path)`, `fail-closed?`, and re-verify it on every config change and on every release branch cut; any new `os.environ.get` or secret-manager lookup must add a row before merge, and any secrets file found in the repo is an immediate gap.

### C2 — Startup and composition root (env accounting, single AppContext, graceful degradation)

Good means `src/investigation_agent_platform/main.py` plus `bootstrap/` and `api/app.py` lifespan build exactly one typed `AppContext`, preserve it across API and worker lifecycles (no silent replacement with in-memory context in production), wire Temporal/Kafka/buffered-dev/job-messaging/dev-seed in a documented order, and degrade explicitly (503 with reason, never silent 200) when dependencies are absent outside production.

Checks: trace `load_application_config_from_env()` → `build_app_context()` → `create_app(container=...)` → lifespan helpers (`_maybe_wire_temporal`, `_maybe_wire_buffered`, `_maybe_seed_dev`, `_maybe_start_job_messaging`); confirm production never takes dev-only paths (`IAP_ENVIRONMENT=production` skips buffered wiring, seed, best-effort Temporal); confirm shutdown calls `shutdown_app_context()` idempotently; confirm every startup branch logs structured start/skip/fail with environment and reason.

### C3 — Telemetry and structured logging (standardized, agent-triagable, file-backed)

Good means every package emits JSON-structured logs through one pipeline (`structlog` configured in `api/app.py` with `merge_contextvars`, `add_logger_name`, `add_log_level`, `TimeStamper`, `format_exc_info`, `JSONRenderer`, plus `sanitize_extra()` redaction in `api/errors.py`), correlated by `tenant_id` and `investigation_id`, written to both console and a rotated log file, and sufficient for an agent or SRE to reconstruct any investigation without reading code.

Required log record shape (all keys snake_case; secrets never logged): `timestamp`, `level`, `logger` (package path, e.g. `investigation_agent_platform.application.worker.activities`), `function` (fully qualified function/activity name), `line` (source line number or `lineno` from the record), `message` (stable human sentence), `tenant_id`, `investigation_id` (when in scope), `event` (stable machine key, e.g. `startup`, `reason_activity failed`, `budget ledger check failed`), `data` (typed attributes relevant to triage: IDs, counts, limits, durations, queue/topic names), `error_type`, `error` (redacted message), `stack_trace` (on `logger.exception` only). Checks per package and per important block: does the happy path log entry/exit with IDs and outcome; does every `except` path use `logger.exception` with `extra` carrying IDs plus `error`; are DB writes, Temporal stage transitions, API decisions, MCP tool calls, and budget/quota denials all represented as log events; is there a log file appender actually creating a file (verify `config/logging.yaml` handlers plus runtime `dictConfig`/volume mount — console-only is a gap); are `extra={...}` dicts passed through `sanitize_extra()` so SecretStr and tokens cannot leak.

### C4 — Domain model (purity, invariants, tenant-first design)

Good means `domain/` holds zero infrastructure imports (except Pydantic v2), aggregates (`Investigation`, `Fact`, `Evidence` + `EvidenceReference`/`EvidenceRelationship`, `Hypothesis`, `Finding`/`InvestigationConclusion`, `ApplicationProfile`) enforce their invariants (UUIDs, optimistic `version`, fingerprint-required evidence, tier-2 content invariant, redaction manifest), and every cross-tenant decision is explicit and redacted.

### C5 — Ports and contracts (typed, tenant-first, versioned evolution)

Good means `ports/` protocols are `runtime_checkable`, take leading `tenant_id`/`investigation_id`, use typed requests (`RuntimeEvidenceRequest`, `ApplicationStateRequest`, `EvidenceQueryResult`), split raw vs intelligence providers (`CodeEvidenceProviderProtocol` vs `CodeIntelligenceProviderProtocol`), and evolve only through versioned, documented changes.

### C6 — Application services and Temporal orchestration (all stages logged, all writes idempotent)

Good means services in `application/` plus `RunInvestigationWorkflow` implement the documented lifecycle (create → contextualizing → investigating → correlate/hypothesize/verify loop → concluding → completed/failed/cancelled, plus `PAUSED`/`AWAITING_INPUT` and `COMPLETED/FAILED → INVESTIGATING` reopen edges), every DB write happens inside an idempotent activity keyed by `idempotency_keys`, every stage transition persists a `timeline_events` row and an `investigation_transitions` row, and halt/cancel flows are signal-based and auditable. Agent-triage lens: can an agent answer from logs plus timeline alone what stage an investigation is in, what evidence qualified, what hypothesis won, and why the loop exited.

### C7 — Persistence (every mutation logged, migrated, isolated, recoverable)

Good means every state mutation has a repository, a SQLAlchemy async model, an Alembic revision, RLS on `tenant_id`, OCC via `version`, and an outbox event where other processes must react; bulk paths (`save_batch`) exist where volume demands; retention/GC policies are explicit. Checks: for each table (`timeline_events`, `investigation_transitions/facts/entities`, `evidence_references`, `findings`, `investigation_conclusions`, `investigation_actions`, `investigation_tool_executions`, `application_profiles`, `idempotency_keys`, `outbox_events`, `action_executions`, knowledge/topology tables) confirm write path, read/hydration path, migration file, and a log line at write time with IDs and outcome.

### C8 — API surface (OpenAPI fidelity, auth, budgets, pagination integrity)

Good means implemented routes match `IAP-implementation-openapi-spec-v1.0.md` (or the spec is updated to match code), tenant scoping and admin auth are enforced, budgets/quotas fail closed with typed errors, and cursor pagination is signed and verified (no raw Elastic `_id` treated as platform evidence ID; platform mints UUIDs on qualification with `evidence_key` mapping).

### C9 — MCP surface (agent interface, not admin surface)

Good means the MCP server exposes only the documented investigation tools over both transports with identical behavior, stdio instances bind exactly one investigation, HTTP identity headers are verified per request, and every tool call logs actor, tenant, investigation, tool name, and redacted result size.

### C10 — Evidence providers and integrations (no stubs, fail-closed registration)

Good means each provider (Elasticsearch, Oracle/SQLcl MCP, Postgres state backend, GitHub/PyGit2 ingest, Neo4j Layer 3, Kafka, S3/MinIO artifacts, LLM gateway) registers only when fully configured with timeouts and ceilings enforced, missing optionals stay unregistered with a named log (never stubbed), and dynamic mapping (`ObservabilitySourceMapping`) resolves tenant scope (`NONE_REQUIRED` vs `FIELD`) per source instead of assuming ECS.

### C11 — Knowledge, memory, and topology (sliced, toggle-gated, provenance-recorded)

Good means execution knowledge (Part 6 envelopes, Mem0/Graphiti behind flags), reference-document retrieval, finding clustering, aggregate reports, chat streaming, background jobs, credential providers, and JSON recovery (Part 11 gaps 1–9) each have a registry/contract, tenant-scoped storage, provenance, quotas, and lifecycle semantics rather than per-feature wiring hacks.

### C12 — Tests, migrations, and operations (runbook truth)

Good means each category above has covering tests (`tests/`), migration history matches models, and Part 9/Part 11 operations docs describe what the code actually does (schedules with overlap/jitter/reconciliation, topic-aware Kafka fan-out per replica, artifact lifecycle, LLM streaming contract, immutable profile revisions).

### C13 — Coding standards (Pydantic inputs, typing, logging, production-ready)

Good means the code follows `~/bin/AGENTS.md` as adapted here, verified per unit rather than assumed from style guides. Mandatory checks: all inputs are Pydantic models — every API route, service method, workflow/activity, MCP tool, and integration entrypoint takes a `BaseModel` with `Field` validation and descriptions (never a raw `dict`), and every API uses separate input vs output models (e.g. `PostCreate` vs `PostRead`, `…Update` for patches) with `response_model` set; everything is fully typed (signatures plus return values, `X | None` never `Optional`, no `Any` without justification, no raw `dict`-shaped inputs where a schema exists); async-first libraries and call sites; keyword (not positional) arguments at call sites; imports at file top (function-level imports only to break cycles); no `print` for logging (per-file `getLogger(__name__)`, leveled logging, `logger.exception` on caught exceptions, `%`-style lazy interpolation in all `logger.*` calls with legacy f-string logs converted plus `noqa: G004` removed when a file is touched); f-strings for general construction, sandboxed Jinja2 only for runtime templates, no `.format()`/`string.Template`, `+` only for static constants at load; no suppressed exceptions (`except: pass` is a gap — log plus re-raise or explicit fallback); all user input validated at the boundary; no custom cryptography; production-ready code only (no stubs for production, no non-production branches inside the main package, dev/prod divergence flagged); settings via typed Pydantic settings with `SecretStr`/`SecretBytes` for secrets, `None` (never `""`) for unset optionals, `Field` descriptions, and the module singleton (never ad-hoc `Settings()` instances); REST verb discipline on routes; migrations immutable after merge (forward-only fixes, tool-generated only, never hand-written), async SQLAlchemy 2.x declarative models, explicit `and_()` (never implicit `where(a, b)`), writer session by default with read-only reader only for explicitly lag-tolerant SELECTs; lowercase filenames; `uv` plus committed lockfile discipline (`uv.lock` never hand-edited); tests added with new code, mirrored under `tests/`, passing before the next unit starts. Log-and-trace verification is empirical: reading a `logger.*` call is not proof — confirm it fires with the expected fields via the log-capture tooling or a focused test run before marking telemetry sufficient.

## 2. Bidirectional per-unit review loop (the actual methodology, repeated for every package and important block)

Run this loop twice per unit — once Doc→Code and once Code→Doc — and record both directions in the traceability matrix. A unit is one reviewable block: a domain aggregate, a port protocol, a service module, one workflow plus its activities, one API router, one persistence model plus repository, one MCP tool, one integration adapter, one bootstrap wiring step, or one config section.

```text
Step 1 - Extract intent: read the doc section and write one sentence for the unit goal (what user capability or guarantee it promises) plus the stated preconditions and failure modes.
Step 2 - Locate code: find the implementing files with glob/grep on symbol names (not memory), record file:line for definitions, callers, wiring (bootstrap/container), routes/tools, models/migrations, and tests.
Step 3 - Read as an SME: read the full function/class, then ask whether the code achieves the Step 1 goal, what it does instead or additionally, and what an on-call engineer would need to know at 2am (inputs, outputs, retries, timeouts, budgets, tenant blast radius).
Step 4 - Trace wiring: confirm the unit is actually reachable (registered provider, mounted router, registered workflow/activity, subscribed topic, scheduled reconciler); unreachable code is a wiring gap even if unit-tested.
Step 5 - Check persistence logging: confirm every mutation persists through a repository inside an idempotent activity/transaction, emits a timeline/transition/outbox row where required, and logs a structured event with tenant_id, investigation_id, outcome, and IDs; missing rows or logs are gaps.
Step 6 - Check telemetry sufficiency: apply the agent-triage test — from logs plus timeline alone, can an agent determine what happened, in which stage/function/line, with which data attributes, and with what exception plus stack trace; if not, file a telemetry gap against C3 with the exact missing fields.
Step 7 - Check contracts and safety: verify Pydantic/Protocol/OpenAPI/MCP schemas, tenant isolation (RLS plus header/protocol scoping), redaction of secrets/PII, budget/quota enforcement, and fail-closed behavior on missing config or denied budget. Then apply the C13 coding-standards gate to the same unit: Pydantic-model inputs (no raw dicts), separate API input/output models, full typing, async-first, keyword args, top-level imports, `%`-style logger calls with `logger.exception` on caught errors, validated user input, and production-ready shape (no stubs, no non-prod branches in the main package).
Step 8 - Judge and classify: assign goal verdict (Achieved / Partially achieved / Not achieved / Exceeded — code does more and better), assign confidence (High/Med/Low with evidence links), and classify divergence per Section 4 (CODE_BETTER → update docs; DOC_EXPECTS or MISSING_BOTH → TODO; STALE → archive note).
```

Reverse direction (Code→Doc) uses the same steps but starts from code: read the block, state what it actually guarantees, then search the docs for that guarantee; undocumented behavior, renamed symbols, changed defaults, new queues/topics/tables, or retired flags each produce either a doc-update note (when code is better) or a TODO (when behavior is missing, unsafe, or unlogged).

## 3. Engineering lenses applied at every Step 3 and Step 6

Apply these questions to each unit and record the answers as evidence, not prose: can an agent triage or investigate from telemetry alone (which stage, which function:line, which tenant/investigation, which data attributes, which exception and stack trace); is every DB persistence accompanied by a log line and a timeline/outbox row so replays are explainable; is every workflow stage (including pause, await-input, cancel, reopen, retry, compensation) both persisted and logged; are timeouts, retries, backoff, jitter, overlap, and idempotency keys explicit and bounded; are budgets, quotas, and concurrency limits enforced before fan-out rather than after; is tenant isolation provable at the port, query (RLS), log (no cross-tenant leakage), and artifact layers; are secrets sourced only from runtime env injection or a secret manager (AWS Secrets Manager, OpenBao, or equivalent), never from `.env` files or any committed secrets file, and redacted in every log path via `sanitize_extra()`; is the happy path plus each failure mode covered by at least one test and one migration where state is involved.

## 4. Divergence taxonomy and code-wins rule

Classify every mismatch exactly once: `CODE_BETTER` means code behavior is correct and docs are stale — update `IAP-functional-view-v0.3.md` and the architecture doc to describe code, citing file:line; `DOC_EXPECTS` means docs promise behavior code does not implement — file a TODO with reproduction (doc section, expected call, actual 404/501/missing wiring); `MISSING_BOTH` means neither docs nor code handles an engineering requirement from Section 1 (e.g. no log file appender, no env-matrix row, unlogged mutation) — file a TODO proposing the standard fix; `STALE` means both agree the behavior is retired — note it for archival without a TODO. When in doubt, re-read the code before re-reading the doc.

## 5. Evidence, confidence, and traceability

Each finding cites `file:line` for code, `doc:section` for docs, plus supporting rows (migration revision, test path, config key, log `event` name). Confidence is High only with definition plus wiring plus test or live log evidence; Medium with definition plus one of wiring/test; Low otherwise (mark for re-check, never for TODO closure). Maintain one traceability table per Part with columns `doc claim`, `code location`, `wiring`, `persistence+log`, `telemetry sufficient?`, `goal verdict`, `classification`, `target (v0.3 section or TODO id)`.

## 6. Outputs and TODO contract

The architecture doc records as-built structure (C4 + sequence + ER views grounded in code, not doc aspirations) with a per-category delta appendix. `docs/IAP-functional-view-v0.3.md` is a full revision of v0.2 (not a diff): carry forward what code confirms, rewrite what code does better, and flag what code does not do with explicit TODO pointers. Gap files live in the review scratch area starting at `001`, five items per file, each item containing `ID`, `title`, `category (C1–C13)`, `problem (observed vs expected with evidence)`, `goal impact (which capability fails and who feels it)`, `fix steps (files to change, config/log/migration/test to add)`, `acceptance (log line, row, route, or test that proves closure)`, and `doc target (v0.3 section to update after fix)`. A TODO is done only when its acceptance artifact exists in code plus logs.

## 7. Execution order (after methodology approval)

Execute categories in dependency order so wiring gaps surface early: C1 config → C2 startup → C3 telemetry → C13 coding-standards gate (applied again inside every later category via Step 7) → C6 workflows → C7 persistence → C4 domain → C5 ports → C8 API → C9 MCP → C10 providers → C11 knowledge/topology → C12 tests/ops; within each category run the Section 2 loop Doc→Code then Code→Doc per Part (Parts 1–11 plus addenda, then openapi-spec, appl-profile, dynamic-mapping, then v0.2 section-by-section). Stop and ask before any destructive action, any secret handling beyond key-name listing, or any scope change to outputs.
