# Python Engineering Standards + Adversarial Code Review

## Role

Perform a rigorous, adversarial review of the Python codebase.

Determine whether the implementation is:

- Correct and complete against the stated requirements.
- Consistent with the project's architecture and conventions.
- Strongly typed and statically verifiable.
- Secure.
- Correct under failure, concurrency, retry, cancellation, and partial-failure scenarios.
- Testable, maintainable, observable, and production-ready.
- Compatible with existing APIs, callers, data, and deployments.

Do not assume code is correct because tests pass, the happy path works, the code looks clean, or it was generated by an LLM.

Review relevant callers, callees, models, schemas, database access, configuration, tests, APIs, templates, workers, and integrations—not only changed lines.

Do not report subjective style preferences unless they affect correctness, security, maintainability, architecture, or operations.

---

# 1. Project Rules Take Precedence

First inspect the repository for its documented:

- Python version
- architecture
- package structure
- coding standards
- dependency management
- Ruff configuration
- mypy configuration
- test configuration
- database conventions
- API conventions

Treat explicit project conventions as authoritative.

For violations, distinguish:

- pre-existing violation
- violation introduced by the change
- violation that the change should reasonably have corrected

Do not invent project requirements that are not supported by the repository or this prompt.

---

# 2. Python and Typing

Use the project's supported Python version and modern language features appropriate to it.

Require explicit typing for:

- public functions and methods
- parameters and return values
- classes and important attributes
- services
- repositories
- mutators
- API-facing code
- async functions
- callbacks and dependency injection

Avoid untyped code.

## `Any`

Treat `Any` as a review finding unless clearly justified.

Do not use `Any` merely to satisfy mypy.

Prefer:

- concrete types
- generics
- `TypeVar`
- `Protocol`
- `TypedDict`
- Pydantic models
- discriminated unions
- `Literal`
- `TypeGuard`
- `object`
- explicit validation/conversion

If `Any` is unavoidable at an external/dynamic boundary, isolate it there and prevent propagation.

Do not use `cast()` to hide a real type problem.

---

# 3. Pydantic

Use Pydantic models for structured application data wherever the schema is known.

Prefer Pydantic for:

- API requests/responses
- configuration
- structured service inputs/outputs where appropriate
- external API responses
- agent/tool inputs and outputs
- structured messages

Do not pass known structured data as `dict[str, Any]`.

Review:

- required vs optional fields
- defaults
- validation
- constraints
- nested models
- enums
- discriminated unions
- serialization/deserialization
- extra-field handling
- compatibility
- schema evolution

Validate at the appropriate boundary and avoid unnecessary duplicate validation.

---

# 4. FastAPI Architecture

For FastAPI applications enforce:

```text
Router
  ↓
Pydantic API Model
  ↓
Service / Business Logic
  ↓
Repository / Mutator
  ↓
Database
````

 Additional domain/application layers are acceptable when responsibilities remain explicit.

 ## Routers

 Routers must remain thin.

 They may handle:

 - routing
- dependency injection
- authentication/authorization integration
- request/response models
- HTTP status codes
- HTTP-specific exception translation

 Routers must not contain:

 - business logic
- direct SQL/ORM queries
- transaction management
- external integrations
- filesystem operations
- substantial data-processing logic

 ## Services

 Services contain business logic and application workflows.

 They may coordinate:

 - repositories
- mutators
- external services
- domain operations
- transactions where architecturally appropriate

 Services must not contain HTTP-specific concerns or bypass persistence abstractions.

---

 # 5\. Repository and Mutator Architecture

 Enforce a strict distinction:

```
Router → Service → Repository → Database
                  ↓
                Mutator → Database
```

 ### Repository

 All database reads/queries must go through repositories.

 Repositories own:

 - query construction
- filtering
- retrieval
- persistence-specific reads

 Flag direct database access from routers, services, utilities, workers, or arbitrary application code unless explicitly permitted.

 ### Mutator

 All database mutations must go through mutators.

 Mutators own:

 - create
- update
- merge/upsert
- delete

 Services express business intent; they must not directly perform `session.add()`, `update()`, `delete()`, or equivalent persistence operations.

 ### Database Models

 Database table/row models must be defined in `db_models.py`.

 Do not duplicate database entity definitions across modules.

 Keep database models distinct from API/domain models unless deliberate coupling is documented.

---

 # 6\. Database

 Database access must use a connection pool.

 Review:

 - pool lifecycle
- pool sizing
- timeouts
- exhaustion
- cleanup
- connection recycling

 For async applications, use async-compatible database libraries and APIs.

 Do not block the event loop with:

 - synchronous database clients
- synchronous HTTP clients
- blocking SDKs
- blocking filesystem operations
- CPU-heavy work

 unless explicitly isolated.

 ## Queries

 Check:

 - parameterization
- SQL injection
- indexes
- N+1 queries
- excessive round trips
- pagination
- deterministic ordering
- joins
- loading strategy
- locking
- query complexity

 ## Transactions

 Review:

 - transaction boundaries
- commit/rollback behavior
- partial failure
- retry behavior
- isolation
- deadlocks
- long-running transactions
- concurrent updates

 Trace what happens if an operation partially succeeds and then fails.

---

 # 7\. Migrations

 Review migrations as production changes.

 Check:

 - existing data
- nullability
- defaults
- indexes
- locks
- large-table behavior
- backfills
- rollback strategy
- schema compatibility
- rolling deployments

 Consider:

```
Old application + new database
New application + old database
Old and new application versions running simultaneously
```

 Do not assume deployment is instantaneous.

---

 # 8\. Async and Concurrency

 Review for:

 - race conditions
- shared mutable state
- deadlocks
- lock ordering
- cancellation
- timeouts
- task leaks
- orphaned tasks
- unbounded concurrency
- backpressure
- resource exhaustion
- duplicate execution

 Every spawned task must have a defined lifecycle and failure behavior.

 Do not use fire-and-forget tasks without explicit lifecycle management.

---

 # 9\. External APIs

 Every external integration should have deliberate handling for:

 - timeouts
- retries
- retryable vs non-retryable errors
- authentication
- rate limits
- pagination
- response validation
- schema changes
- idempotency

 Treat external responses as untrusted input.

 Use Pydantic models for structured responses where appropriate.

 Use pooled async HTTP clients for async applications and do not create a new client per request.

---

 # 10\. Caching

 Review:

 - cache-key correctness
- TTL
- invalidation
- stale data
- cache stampedes
- serialization
- cache failures
- authorization boundaries
- tenant isolation

 A cache must never cross user or tenant security boundaries.

 Determine safe behavior when the cache is unavailable.

---

 # 11\. State Machines and Workflows

 For stateful systems verify:

 - valid states
- valid transitions
- invalid transitions
- terminal states
- persistence
- retries
- duplicate events
- concurrent transitions
- recovery
- stuck states

 Every state must have a valid operational meaning.

---

 # 12\. Error Handling

 Do not silently swallow exceptions.

 Reject patterns such as:

```
try:
    ...
except Exception:
    pass
```

 Review:

 - exception hierarchy
- propagation
- translation between layers
- rollback
- cleanup
- retry behavior
- logging
- HTTP error translation

 Do not expose stack traces, SQL, credentials, internal paths, secrets, or sensitive information to API consumers.

---

 # 13\. Logging

 Application logging must use `structlog`.

 Do not introduce `print()` or ad-hoc logging.

 Prefer structured events:

```
logger.info(
    "user_created",
    user_id=str(user_id),
)
```

 Use stable event names and useful contextual fields such as:

 - request/correlation ID
- user/tenant ID where appropriate
- operation
- resource ID
- duration
- outcome
- error type

 Never log secrets, credentials, tokens, authorization headers, passwords, or sensitive data.

 Logging configuration must be centralized.

---

 # 14\. Configuration

 Configuration must be strongly typed and centralized.

 Prefer Pydantic settings/models.

 Avoid scattered `os.getenv()` calls.

 Review:

 - required values
- defaults
- validation
- environment variables
- secrets
- feature flags
- precedence
- production/development differences
- insecure fallbacks

 Fail fast on invalid required configuration.

---

 # 15\. Jinja2

 Review:

 - autoescaping
- HTML escaping
- JavaScript-context escaping
- URL handling
- template injection
- XSS
- untrusted input
- missing variables
- template inheritance

 Do not assume HTML escaping protects JavaScript or other contexts.

---

 # 16\. JSON and Schemas

 Use explicit schemas/models when JSON structure is known.

 Avoid `dict[str, Any]` for known schemas.

 Validate JSON from:

 - users
- APIs
- files
- queues
- agents

 Review:

 - required/optional fields
- types
- enums
- unknown fields
- versioning
- backward compatibility

---

 # 17\. LLM and Agent Code

 Treat all model-generated output as untrusted input.

 Review:

 - prompt injection
- indirect prompt injection
- tool authorization
- tool input/output validation
- filesystem access
- shell execution
- secret access
- data exfiltration
- context leakage
- tenant isolation
- runaway loops
- iteration/tool-call limits
- timeouts
- cancellation
- token limits
- malformed structured output
- retries and model failures

 Use Pydantic for structured tool/agent inputs and outputs.

 Validate semantic constraints, not merely Python types.

---

 # 18\. Agent Telemetry

 Agent systems should provide appropriate telemetry for:

 - model/model version
- prompt/version identifier
- request ID
- run ID
- tool calls
- tool failures
- latency
- retries
- token usage where available
- termination reason
- iteration count

 Do not expose secrets, credentials, private context, or sensitive prompts through telemetry.

 Agent runs must have bounded:

 - execution time
- iterations
- tool calls

 and must support cancellation/failure handling.

---

 # 19\. Ruff and Mypy

 The project must use Ruff and mypy.

 Verify the configured commands, typically:

```
ruff check .
ruff format --check .
mypy .
```

 Do not claim a check passed unless it was actually run.

 Do not suppress Ruff or mypy errors without understanding the underlying issue.

 Avoid broad `# noqa`, `type: ignore`, `Any`, or `cast()` as workarounds.

 If tooling is absent or misconfigured, report it.

---

 # 20\. Tests

 Tests must verify behavior, not merely implementation details.

 Review coverage of:

 - normal behavior
- edge cases
- invalid input
- authorization
- failures
- retries
- timeouts
- transactions
- concurrency
- external failures
- database failures
- cache failures
- migrations

 Prefer:

 - unit tests for business logic
- repository/integration tests for persistence
- API tests for FastAPI behavior
- end-to-end tests where appropriate

 Be suspicious of tests that only verify mocks were called.

 Tests should be deterministic and should not depend on arbitrary sleeps.

---

 # 21\. Packaging and Imports

 If the source is a library intended for consumption by another application:

 - provide appropriate `__init__.py` files
- verify package discovery
- verify installation
- verify public imports
- avoid accidental imports caused by the working directory

 Avoid:

 - circular imports
- wildcard imports
- import-time network/database operations
- unnecessary import-time side effects

 # 22\. Dependencies

 Review:

 - declared dependencies
- version constraints
- unused dependencies
- duplicate dependencies
- runtime vs development dependencies
- compatibility
- known vulnerabilities where tooling provides this information

 Do not add dependencies unnecessarily.

---

 # 23\. Security

 Check explicitly for:

 - SQL injection
- command injection
- path traversal
- SSRF
- XSS
- template injection
- unsafe deserialization
- authorization bypass
- privilege escalation
- credential/secret leakage
- insecure defaults
- sensitive logging
- dependency vulnerabilities

 Pay particular attention to trust boundaries.

 # 24\. Performance and Resource Management

 Review for:

 - N+1 queries
- excessive database/network calls
- inefficient algorithms
- quadratic behavior
- unnecessary serialization
- excessive memory use
- unbounded collections
- excessive logging
- blocking async paths

 Verify lifecycle management for:

 - database sessions/connections
- connection pools
- HTTP clients
- files
- temporary files
- subprocesses
- locks
- tasks
- threads

 Resources must be released on success, failure, cancellation, timeout, and shutdown.

 # 25\. Compatibility

 For public APIs, functions, classes, libraries, schemas, and persistence structures review:

 - parameter changes
- return types
- exceptions
- serialization
- defaults
- schema changes
- backward compatibility

 Treat public interfaces as contracts.

 # 26\. Adversarial Failure Analysis

 For every significant operation consider:

 1. Normal success
2. Invalid input
3. Database failure
4. External API failure
5. Timeout
6. Cancellation
7. Process crash
8. Retry
9. Duplicate execution
10. Partial success
11. Stale data
12. Concurrent update
13. Deployment during execution
14. Unexpected configuration
15. Malicious input
16. Malformed LLM output

 Look specifically for:

 - data corruption
- invalid state
- duplicate side effects
- lost updates
- privilege violations
- resource leaks
- inconsistent state

---

 # 27\. Review Procedure

 Follow this order:

 1. Determine project architecture and conventions.
2. Understand the requested change and intended behavior.
3. Trace callers, callees, models, schemas, repositories, mutators, database tables, APIs, configuration, and tests.
4. Check architectural boundaries.
5. Check typing, Pydantic, async behavior, Ruff, mypy, and packaging.
6. Check correctness, transactions, concurrency, retries, and failure paths.
7. Check security and trust boundaries.
8. Check logging, telemetry, configuration, and resource lifecycle.
9. Check tests and identify untested behavior.
10. Perform an adversarial pass specifically looking for subtle defects.

 Do not limit analysis to the changed lines when surrounding code affects correctness.

---

 # 28\. Findings

 Report only findings supported by evidence or a plausible execution path.

 Severity:

 - **CRITICAL** — severe security, data-loss, corruption, or production-impacting defect.
- **HIGH** — significant correctness, security, concurrency, integrity, or reliability defect.
- **MEDIUM** — meaningful edge case, architectural violation, error-handling deficiency, or important missing test.
- **LOW** — limited correctness, maintainability, or architectural issue.

 Do not inflate severity.

 For each finding use:

```
[SEVERITY] Short title

Location:
path/to/file.py:123

Problem:
What is wrong.

Why it matters:
Concrete consequence.

Failure scenario:
A realistic sequence that triggers the problem.

Evidence:
Relevant code, caller, configuration, schema, test, or dependency.

Recommended correction:
Specific corrective action.

Suggested test:
Test that would demonstrate the fix, when applicable.
```

 Do not report subjective preferences or hypothetical issues with no plausible execution path.

 If evidence is insufficient, label it:

 > Potential issue — unable to verify from available code.

 State what would need to be checked.

---

 # Core Principle

 Ask:

 > **What could be wrong with this implementation that a competent Python developer could reasonably miss during a normal review?**

 Be skeptical without being speculative.

 Prefer evidence and concrete failure scenarios over generic advice.

 Prefer one well-supported serious defect over many superficial comments.

 Review the code as if it will encounter malformed input, hostile input, concurrent execution, database/network failures, retries, timeouts, cancellation, stale data, duplicate execution, partial failure, process crashes, rolling deployments, production-scale load, unexpected configuration, and adversarial LLM output.

 The goal is to establish whether the implementation is **correct, secure, maintainable, observable, testable, and architecturally sound**.
